The diagrams in my posts are real Excalidraw scenes, not screenshots. Each one is a JSON file in this repo; a small React island turns it into an SVG when you scroll near it and shows it in whichever theme the site is in.

<Callout tone="answer">Draw in Excalidraw, save the scene as JSON under `web/public/diagrams/`, and write `<ExcalidrawBoard src="/diagrams/name.json" />` in the post. Everything else happens on its own.</Callout>

Here is the whole pipeline, drawn as one of these boards. Hover it for zoom controls, drag to pan, or open it larger.

## Why not just export an image

A PNG is fine when a diagram has one right view. Mine usually don't. I want boxes you can zoom into, text that stays sharp, and lines that make sense in both the dark and light theme.

An image gives me none of that without extra work. I'd export twice, once per theme, and re-export every time I nudge an arrow. A scene file is one source of truth: I edit it, commit it, and the page picks it up.

The trade-off is weight. Excalidraw is a full drawing app, and its main chunk is about 1.1 MB (around 370 KB gzipped) in my build. Most of this post is about making sure you only pay for that when a board is actually on screen.

## Where the scenes live

Every board is a plain file in `web/public/diagrams/`. Astro copies that folder as-is, so `web/public/diagrams/board-pipeline.json` is served at `/diagrams/board-pipeline.json`.

The file is the same document Excalidraw saves when you download a scene:

```json
{
  "type": "excalidraw",
  "version": 2,
  "source": "https://excalidraw.com",
  "elements": [],
  "appState": { "viewBackgroundColor": "transparent" },
  "files": {}
}
```

`elements` holds the shapes, arrows and text. `files` holds any pasted images as data URLs. Keeping scenes in git means each diagram is versioned next to the post that uses it, and a broken one shows up in review instead of in production.

## Putting a board in a post

In MDX it is one line, and there is no import:

```mdx
<ExcalidrawBoard src="/diagrams/example-stack.json" />
```

That works because the writing page hands the component to MDX, the same way it already hands over `<Callout>`:

```astro
<Content components={{ Callout, ExcalidrawBoard }} />
```

Boards are 500px tall by default and drop to 360px on narrow screens. A small diagram can ask for less room:

```mdx
<ExcalidrawBoard src="/diagrams/example-stack.json" height={360} />
```

## Why it waits until you scroll

Astro renders this page as static HTML. Interactive pieces are "islands": components that get their JavaScript only when a hydration rule says so. The rule here is `client:visible`, which waits until the board is about to enter the viewport.

Posts never write that directive themselves. A thin Astro wrapper adds it:

```astro
---
import Board from './ExcalidrawBoard.tsx'
const { src, height } = Astro.props
---

<Board client:visible src={src} height={height} />
```

There is a second, smaller delay inside the island. Its own chunk is about 6 KB, and it only pulls in the Excalidraw library with a dynamic `import()` once it has mounted. So a reader who never scrolls this far never downloads the drawing app at all, and pages without a board don't reference it.

While the library and the scene load, the board shows a faint "Whiteboard" label at its final height. When the drawing is ready, the label fades out and the SVG fades in. Nothing below it jumps.

## From scene to SVG

I don't need an editor on the page, only the picture. Excalidraw ships the function it uses for its own "Export image" button, and that's the only thing the island calls:

```tsx
const { exportToSvg } = await import('@excalidraw/excalidraw')
const svg = await exportToSvg({
  elements: scene.elements,
  appState: { ...scene.appState, exportBackground: false, viewBackgroundColor: 'transparent' },
  files: scene.files,
  exportPadding: 16,
  skipInliningFonts: true,
})
```

What comes back is an ordinary `<svg>` element. The text stays text and every line stays sharp at any zoom. There's no canvas to size and no editor state to keep in sync.

Fitting it is plain arithmetic. The SVG's `viewBox` gives its natural size, a `ResizeObserver` gives the frame's, and the scale is the smaller of the two ratios, capped at 1. Big drawings shrink to fit; a three-box sketch stays the size I drew it.

`skipInliningFonts` matters more than it looks. By default the export embeds the hand-drawn font inside the SVG, which means downloading a 1.8 MB font-subsetting script and fetching the font from a CDN. I host Excalifont and Virgil myself instead, declare them with `@font-face`, and wait for them before the fade starts, so the text never swaps mid-animation.

## Following the site theme

The theme toggle in the header sets `data-theme` on the `<html>` element. The board doesn't watch it at all. One CSS rule does the work:

```css
html[data-theme='dark'] .excal-stage svg {
  filter: invert(93%) hue-rotate(180deg);
}
```

That's the same filter Excalidraw uses for its own dark mode. Inverting flips dark strokes to light, and the hue rotation puts colours back roughly where they were. Flip the toggle now; the boards switch in the same frame as the page, with nothing re-rendered.

So I draw every scene in light mode with dark strokes, and dark mode turns them light. The background is transparent, so the board sits directly on the page colour instead of in a box.

<Callout>If a diagram looks faint in dark mode, it was probably drawn with light strokes. Redraw it with dark ones in Excalidraw's light theme.</Callout>

## Controls that stay out of the way

The drawing is the point, so the controls hide until you want them. Hover a board, or tab into it, and a small pill shows up in the corner: zoom out, the current zoom, zoom in, reset, and open larger. On touch screens it simply stays visible. Dragging the drawing pans it. The scroll wheel is left alone, because a diagram that hijacks scrolling halfway down an article is a trap.

"Open larger" puts the same SVG in a centred panel at about 70% of the screen, over a blurred copy of the page. Click anywhere outside the panel, press Escape, or hit the close button to go back. Focus moves to the close button on the way in and returns to where you were on the way out.

## What failed: a live canvas

The first version embedded the actual Excalidraw app in view mode. It worked, but it never felt like part of the page. Every board flashed an empty white canvas before the drawing appeared. The editor's stylesheet, about 145 KB, ended up in the CSS shared by every post, whether it had a board or not. And I spent more CSS hiding the app's menus and toolbars than styling the board itself.

Swapping it for an SVG removed all three problems at once. The drawing app still loads on posts with a board, because the export function lives inside it, but nothing of it stays on screen.

## Adding a new board

This is the full workflow I follow:

1. Draw the diagram at excalidraw.com in the light theme, with dark strokes and the default hand-drawn font.
2. Download the scene from the main menu with "Save to…". You get a `.excalidraw` file, which is already JSON.
3. Rename it to `<name>.json` and move it into `web/public/diagrams/`.
4. Add `<ExcalidrawBoard src="/diagrams/<name>.json" />` where it belongs in the post.
5. Run `npm run dev:web`, then check the board in both themes and try the zoom controls and "Open larger".
6. Run `npm run build:web` before pushing.

Keep pasted screenshots out of scenes when you can. They're stored inside the JSON as data URLs, and a single one can make the file several times bigger than the drawing itself.

## What I left out on purpose

There's no editing in the browser. Diagrams change in Excalidraw and land through a commit, like the rest of the site.

There's no outside storage either. Scenes are static files, served from the same place as everything else.

Boards also stay inside Writing posts. The home page, projects and moods don't need a drawing app, so they don't load one.

## What I'd change next

The weak spot is that the SVG is still made in the browser. RSS readers and no-JS browsers only get the placeholder, and readers still download the drawing app just to run one export. Rendering the SVG at build time would fix both, and it's the next thing I'd add.

Until then, the rule is simple: a board illustrates the text, it never replaces it. If the post doesn't make sense with the diagram missing, the words need more work.
