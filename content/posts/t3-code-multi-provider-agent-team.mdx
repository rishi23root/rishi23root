I use [T3 Code](https://github.com/pingdotgg/t3code) as the one place where my coding agents live. It is an open-source (MIT) app that drives the agent CLIs already signed in on my machine. I have Claude Code, Codex, Cursor and Antigravity connected.

## TL;DR

<Callout tone="answer">One orchestrator thread reads the task, rewrites the brief, picks a model and hands the work to a child. The rules are written for any provider, but the one build I have measured ran on Claude models only: five helpers used 548,808 tokens. An Opus review that read the result cold found 25 issues, 1 of them critical, and all were fixed before the first commit.</Callout>

The rules, short: the manager hires and workers never do; spend by how hard the thinking is; hand off at 50–65% of the context window; and never let a model review its own work.

## What problem I had

I was folding discovery, design, coding and review into one long chat. Several issues stacked in one window meant the agent had to compact, and after that it drifted or re-read history that no longer mattered.

Switching providers made it worse. A run would go to one provider and die on quota in the middle of a question, with a message like "resets in 151h43m". I had no rule for which model should take which job, and nothing was written down after a run finished.

I needed three things: small contexts, a deliberate choice of model per task, and a second pair of eyes that had not written the code.

## What I tried

1. **One long thread for everything.** It works until the window fills. Then the cost is compaction and drift.
2. **A fixed lookup from role to model.** Simple, but it ignored quota. One run went to two models on the same provider, and both failed with "Individual quota reached… resets in 164h30m".
3. **One orchestrator thread with a few hard rules.** This is what I kept.

## What worked

### Subagent or its own thread

T3 Code gives an agent two ways to hand work off. `delegate_task` starts a child inside the current thread; it gets only the task text and none of the parent's history. A new thread is a separate conversation that can be bound to its own git worktree.

My rule is to decide by where the result lands:

- The change belongs on the pull request this session is already building: **subagent**.
- The change needs its own pull request: **its own thread**, with its own worktree, for one issue and one PR.
- Review is always a different thread from the one that wrote the code.

A builder thread starts empty and reads one issue. The notes, the other tickets and the original request stay with the orchestrator.

### Seats and caps

I use four seats: junior, mid, senior and 10x. Senior is the manager, the only seat allowed to approve a fan-out. Depth stops at manager to worker. A worker that needs help asks the manager; it does not hire.

The caps are small on purpose. While piloting: 1 build and 1 review in flight. In steady state: at most 4 builds and 2 reviews, 6 coding agents in total. Before a second builder starts, the two tickets must touch different files and a review slot must be free, because my own reading of PRs is the real bottleneck.

### Spend by how hard the thinking is

Task size is a poor guide to model choice. A large task is mostly reading, and reading is cheap work. So the tiers follow the kind of thinking:

| Tier | Work | Seat |
| --- | --- | --- |
| 3 | Search, reading, log parsing, intake | junior, helpers |
| 2 | Features, tests, bug fixes in known modules | mid |
| 1 | Architecture, security, a cold review, a stuck decision | senior, 10x |

One quota rule sits on top: at 15% remaining or below, no new work starts on that model. I switch provider at the same tier first and drop a tier only if nobody has room. Before this I had three thresholds written in three places (10%, 15% and 5%) and they disagreed. I picked 15% and deleted the other two.

### Hand off at 50–65% context

This rule is written but I have not yet measured a handoff. When a thread reaches 50–65% of its window, it writes a memory note on the GitHub issue or PR: goal, decisions, open questions, links, next action and files in play. Then the work continues in a fresh context that reads only the issue, the PR and that note. The note lives on GitHub, so any model on any provider can pick it up.

## What failed

### Prose is not a mechanism

I wrote the whole loop as instructions: read the task, rewrite the brief, pick the model, place the run, log it. Then I asked Claude to review the design. The run log that model choice was supposed to learn from had zero rows. Its only writer was a sentence telling an agent to append a line, and agents skip bookkeeping under load. Two of the tools the instructions named did not exist in that session.

The fix is boring: a hook writes the log, not the agent, and success is judged from CI and merge, not from the worker saying "done".

### A parallel notes agent wrote stale facts

While one agent set up a server, I had a second one keeping notes. It wrote "disk not wiped" while the disk was being wiped, and the main agent had to correct it. Two agents writing about the same moving state will disagree. Now the agent doing the work writes the notes.

### Quota died mid-run

The two quota failures above are why the floor exists. Both happened in the middle of a run, not at the start, so the work in progress was lost. A related surprise: one provider looked broken when it was simply not logged in.

### An agent deleted `.gitignore`

During a sync of a private notes repo, the agent deleted `.gitignore` and restored it in a follow-up commit. A secrets scan of that repo came back clean, but an agent with write access will sometimes remove the file that protects you.

## Architecture

In words: the orchestrator thread reads the issue, writes the brief and picks the model. A helper started with `delegate_task` works in the orchestrator's checkout and its result lands on the current PR. A builder thread gets its own worktree, takes one issue and opens one PR. Every PR goes to a review thread run by a different model. Arrows only go down: the manager starts workers, and workers start nothing.

The provider names in the drawing are examples. Any child can run on any connected provider that has quota left.

## Code

There is very little code. The handoff to a subagent is one tool call. The values in angle brackets are placeholders; the option names come from what each provider reports:

```json
{
  "task": "<the rewritten brief: goal, constraints, done-when, files in play>",
  "role": "review",
  "mode": "async",
  "target": {
    "providerInstanceId": "<provider>",
    "model": "<a tier 1 model>",
    "options": { "effort": "high" }
  }
}
```

A builder thread gets a short, fixed prompt next to the issue URL:

```text
Implement this issue only. Follow the agent brief.
Stop and comment if a needed fact is missing.
Open one PR. Do not take a second issue. Do not launch threads.
```

And every ticket carries a block that says what it may touch, which is how the manager checks that two builders won't collide:

```markdown
### Technical Dependencies
- **Seat:** `junior` | `mid` | `senior`
- **Risk:** `normal` | `high`
- **Touches:** `src/auth/*`, `src/middleware/session.ts`
- **Must not touch:** `src/billing/*`
- **Seam to test:** `POST /api/logout` integration test
```

## Results

The numbers are what the agent harness reported for each child run when it finished; I did not ask for them.

**The reader.** For the design review, a Sonnet subagent read my notes and the strong model did only the judgement. The reader used 82,788 tokens in 61 seconds across 17 tool calls.

**The five-helper build.** I had a strong Claude model manage and write a new version of my agent skills (a private repo). Five helpers did the reading and checking:

| Helper | Model | Tokens | Time |
| --- | --- | --- | --- |
| Research on four public skill setups | Sonnet | 92,163 | 117 s |
| Findings document from my notes | Sonnet | 82,441 | 37 s |
| Close reading of 4 upstream repos | Sonnet | 142,163 | 156 s |
| Independent review of the whole repo | Opus | 160,826 | 323 s |
| Behaviour test: follow the skills on 5 requests | Sonnet | 71,215 | 78 s |

That is 548,808 tokens across 5 runs. The one tier 1 run, the Opus review, was 29% of it.

That review found 25 issues, 1 critical: one kind of task had no step that wrote the list of files a ticket may touch, so the junior seat would have refused its own first ticket. All 25 were fixed before the first commit. The behaviour test passed all 5 requests and reported 13 unclear sentences.

What is not proven: this build ran on Claude models only, and no real ticket has yet gone through build, review and ship under these rules. The pilot is one issue, one thread, one PR.

## What I recommend

Keep one manager and make it small. It should see conclusions, not file dumps. Send the reading to a cheap model and keep the strong one for judgement.

Have a different context review the work. The author model missed a critical gap that a cold reader found. That review was the most expensive run in the build and I would pay it again.

Turn any rule that matters into a mechanism. A sentence that says "log the run" produced zero rows.

Don't do thread-per-issue if you pay per token and the tasks are small. Don't run a team at all for a change you can describe in two lines; one thread is enough. And keep the caps low until one issue has gone all the way through.
