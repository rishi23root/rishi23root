I keep one folder of content in the repo, and two builds read it: one writes my GitHub profile README, the other builds this site. Everything else here (the writing pipeline, the diagrams, the small touches on the home page) is built so that folder stays the only place I edit.

## TL;DR

<Callout tone="answer">Put the words in one place and let each surface render them its own way. Here `content/site.json` and `content/posts/` feed both the README and an Astro site; JavaScript is opt-in per page; diagrams are Excalidraw scenes turned into SVG; and the feeds machines read (RSS, `llms.txt`, sitemap, structured data) come from the same files.</Callout>

## What problem I had

My GitHub profile README has been generated by a script since 2023: a markdown template, a TypeScript config with my bio and featured repos, and a build that fills in stats from the GitHub API. That was fine while the README was the only place I described myself.

Then I wanted a real website with writing on it, and every fact suddenly had two homes. The bio, the mottos, the featured projects and the contact links would live in the README's config and again somewhere in the site. Every new post would need a title, date and link added to the README by hand. Two copies of the same words drift; it's only a question of how fast.

I also wanted more than a plain blog: diagrams I could still edit after publishing, a home page with some personality, and pages that stay light on a phone. Most ways of getting those extras quietly put a framework on every page.

## What I tried

1. **Keeping the README's config as the source.** The site could import `config.ts` directly. But then the site depends on the README build's code, and the data stays locked in a TypeScript file only one build understands.
2. **Making the site the source.** Generate the README from the built site. That turns a thirty-line template into a scraper, and the README build would need the whole site build to run first.
3. **Moving the data into plain files both builds read.** Bio, mottos, links and featured repos went into `content/site.json`, and posts into `content/posts/*.mdx`. `config.ts` became a few re-exports. Each build loads those files and ignores what it doesn't need.

For diagrams I weighed exported images first, then embedded a live Excalidraw canvas, and finally settled on an SVG rendered from the scene file.

## What worked

The shared folder. Each surface owns its layout, and neither owns the words.

### The README build

`readme.template.md` is about thirty lines: a fenced `whoami` block and a handful of HTML comment markers like `<!-- recent_posts_inject -->`. `index.ts` loads `content/site.json` (through a thin `config.ts`), fetches stats, featured repos and recent stars from the GitHub API, renders each block, and swaps it in for its marker.

The posts list doesn't need Astro. `posts.ts` reads the MDX files directly, pulls `title`, `date`, `slug`, `summary` and `draft` out of the frontmatter, skips drafts, and writes links to `/writing/<slug>` on this site. A GitHub Action runs the build on every push to `master` and commits `README.md` only if it changed.

### The writing pipeline

On the site, posts are an Astro content collection loaded straight from `../content/posts`. The schema is where I put the rules I kept breaking by hand:

- `title` is at most 90 characters and `summary` at most 220, because the summary is reused as the meta description, the social card text, the RSS line and the `llms.txt` entry.
- `slug` must be kebab-case and must equal the file name. A small check fails the build otherwise, so a renamed file can't quietly change a URL.
- `draft: true` shows the post in `npm run dev:web` and hides it everywhere else.

Every post follows the same section order: TL;DR, the problem, what I tried, what worked, what failed, architecture, code, results, and what I'd recommend. You're reading one. The order forces me to write down the failures, which is usually the part worth reading. A private draft template in the repo has the skeleton, and the post page builds its "On this page" rail, reading time and FAQ from the headings and frontmatter.

### Diagrams as SVG

A diagram is an Excalidraw scene saved as JSON under `web/public/diagrams/`, and in a post it's one line with no import:

```mdx
<ExcalidrawBoard src="/diagrams/board-pipeline.json" />
```

That line renders this:

<ExcalidrawBoard src="/diagrams/board-pipeline.json" height={420} />

A thin Astro wrapper hydrates the component with `client:visible`, so nothing happens until the board is about to scroll into view. Then it loads Excalidraw, calls `exportToSvg` once, fits the result to the frame and fades it in. Hover it and a small control bar shows up for zoom, reset and expand. Drag pans; the scroll wheel stays with the page.

Dark mode is one CSS filter on the SVG, the same invert-and-rotate Excalidraw uses for its own dark theme, so I draw every scene in light mode with dark strokes. The hand-drawn fonts are hosted here, so a board never reaches out to a CDN.

### Small things that make it feel like mine

**Moods.** On desktop, the home page shows one of seven still images next to the text, with a small "next mood" button and a link to see them all. The order is a shuffle bag kept in `localStorage`: every mood shows once before any repeats, and a new round never opens with the image you just saw. The first pick happens in an inline script in `<head>`, which preloads that image before React has even downloaded. The island only hydrates at 1024px and up, so phones never load it. All of them live on `/mood`.

**Command palette.** Press <kbd>⌘K</kbd>, <kbd>Ctrl</kbd>+<kbd>K</kbd> or <kbd>?</kbd> anywhere for a palette of pages, projects and posts, plus "Toggle theme". There's no button for it. A 1.1 KB listener ships on every page; the palette itself is 3.7 KB of plain TypeScript, fetched on first open. Two-key chords (<kbd>G</kbd> then <kbd>W</kbd> for Writing) work without loading it at all.

**Themes.** Pages ship dark. A tiny inline script in `<head>` applies a saved light choice before the first paint, so there's no flash of the wrong theme. The toggle writes to `localStorage`, and everything that has colour, including the diagrams, follows the `data-theme` attribute on `<html>`.

**SEO and machine-readable copies.** Every page gets a canonical URL, Open Graph and Twitter tags, and a social image. Posts add `BlogPosting`, `BreadcrumbList` and, when there's an FAQ, `FAQPage` structured data. RSS, the sitemap and `llms.txt` are generated from the same posts and `site.json` at build time, so there's no hand-kept copy in `public/` to go stale. `robots.txt` allows search and AI crawlers. Old `/blog/<slug>` links redirect to `/writing/<slug>`.

## What failed

**The live Excalidraw canvas.** My first version embedded the real Excalidraw app in view mode. Every board flashed an empty white canvas before the drawing appeared. The editor's stylesheet, about 145 KB, landed in the CSS shared by every post, with or without a board. I spent more CSS hiding Excalidraw's menus than styling the board. Swapping to SVG fixed all three.

**A CSS import that only worked sometimes.** Excalidraw exports its stylesheet under `development` and `production` conditions, with no default. A plain `import '@excalidraw/excalidraw/index.css'` built fine and then failed in local dev with "Cannot find module". A Vite alias fixed it for me and not for everyone else. The real fix was not importing the package statically at all: the component loads it with a dynamic `import()` in the browser, so the server never tries to resolve it.

**Letting the export inline its fonts.** By default `exportToSvg` embeds the hand-drawn font inside the SVG. That means a 1.8 MB font-subsetting script, a worker that failed and fell back to the main thread, and a font fetched from a CDN. Turning that off and hosting the two fonts myself (about 140 KB, split by character range so a page fetches only what it uses) removed all of it.

**Trusting the first error message.** After a dependency change, the dev server threw `jsxDEV is not a function` and the boards stayed blank. It looked like a broken component. It was a stale Vite pre-bundle cache. `rm -rf web/node_modules/.vite` and a restart fixed it. When a dev-only error makes no sense, clear the cache before reading the stack trace.

<Callout>A headless test browser can also lie to you: Chrome in headless mode reports `hover: none`, so styles meant for touch screens apply and hover-only UI looks permanently visible. Force a mouse pointer before trusting a hover test.</Callout>

## Architecture

<ExcalidrawBoard src="/diagrams/site-architecture.json" height={460} />

In words: `content/` holds the data. The README build reads the bio and post titles and writes `README.md`, which GitHub shows on my profile. The Astro site reads everything and deploys to GitHub Pages. Two workflows, both triggered by pushing to `master`: one only rewrites the README, the other only deploys the site, and the deploy runs only when `web/` or `content/` changed.

| Piece | Reads | Writes |
| --- | --- | --- |
| `index.ts` + `posts.ts` | `site.json`, post frontmatter, GitHub API | `README.md` |
| Astro (`web/`) | `site.json`, full posts, `web/public/diagrams/` | pages, RSS, sitemap, `llms.txt` |
| `ExcalidrawBoard` island | one scene JSON | an inline SVG, in the browser |

## Code

The README side is plain string work. This is the whole posts block:

```ts
export async function renderRecentPosts(siteUrl: string, limit = 5): Promise<string> {
  const posts = (await listPosts()).slice(0, limit)
  if (!posts.length) return '_No posts yet._'
  const base = siteUrl.replace(/\/$/, '')
  return posts
    .map((p) => `- **[${p.title}](${base}/writing/${p.slug})** — ${p.date}`)
    .join('\n')
}
```

The site side leans on the schema. Trimmed to the parts that matter:

```ts
const posts = defineCollection({
  loader: glob({ pattern: '**/*.{md,mdx}', base: '../content/posts' }),
  schema: z.object({
    title: z.string().min(1).max(90),
    date: z.coerce.date(),
    slug: z.string().regex(/^[a-z0-9]+(?:-[a-z0-9]+)*$/),
    summary: z.string().min(1).max(220),
    draft: z.boolean().default(false),
    faq: z.array(z.object({ q: z.string(), a: z.string() })).default([]),
  }),
})
```

And the diagram export, which is the only Excalidraw function the site calls:

```tsx
const { exportToSvg } = await import('@excalidraw/excalidraw')
const svg = await exportToSvg({
  elements: scene.elements,
  appState: { ...scene.appState, exportBackground: false, viewBackgroundColor: 'transparent' },
  files: scene.files,
  exportPadding: 16,
  skipInliningFonts: true,
})
```

The full files are `posts.ts`, `web/src/content.config.ts` and `web/src/components/ExcalidrawBoard.tsx` in the [repo](https://github.com/rishi23root/rishi23root).

## Results

I measured these from the production build (`npm run build:web`) and the browser's network panel:

- **One edit, both surfaces.** Changing my bio or publishing a post is one commit. The README and the site both pick it up on the next push to `master`, with no copy step.
- **A plain post ships no React.** Its scripts are the 1.1 KB palette listener; the shared stylesheet is 37.5 KB (8.3 KB gzipped). The home page HTML is about 21 KB.
- **React is opt-in.** The mood island is 7.5 KB plus the React runtime (66 KB gzipped), only on desktop. A post with a diagram adds a 6 KB island and, once a board scrolls into view, the Excalidraw library (about 1.1 MB, 372 KB gzipped).
- **Diagrams got lighter.** Moving from the live canvas to SVG took 145 KB of CSS off every post. Self-hosting fonts took a 1.8 MB script and a CDN request off every board.
- **Drafts can't leak.** One flag hides a post from pages, RSS, the sitemap, `llms.txt` and the README list, because all five read the same field.

## What I recommend

Share data, not layout. A JSON file and a folder of MDX are boring on purpose: any build can read them, and none of them owns the others. The README generator here is a template, a few markers and string replacement. Keep yours that dumb.

Make JavaScript earn its place per page. Astro's `client:visible` and `client:media` did most of the work. A feature that only matters on desktop shouldn't cost a phone anything.

If you embed diagrams, render them to SVG. I'd go one step further than I have: render the SVG at build time. Readers would skip the 1.1 MB download, and RSS readers and no-JS browsers would see the diagram instead of a placeholder. That's the next change I'm making.

Don't do this if you only want a blog. A hosted platform will get you writing sooner. This setup pays off when you have more than one surface to keep in sync and you'd rather edit a file than a dashboard.
