I keep one folder of content in the repo, and two builds read it: one writes my GitHub profile README, the other builds this site. Everything else here (the writing pipeline, the diagrams, the small touches on the home page) is built so my bio and my posts live in that folder and nowhere else.

## TL;DR

<Callout tone="answer">Put the words in one place and let each surface render them its own way. Here `content/site.json` and `content/posts/` feed both the README and an Astro site; JavaScript is opt-in per page; diagrams are Excalidraw scenes turned into SVG; and the feeds machines read (RSS, `llms.txt`, sitemap, structured data) come from the same files.</Callout>

## What problem I had

My GitHub profile README has been generated by a script since 2023: a markdown template, a TypeScript config with my bio and featured repos, and a build that fills in stats from the GitHub API. That was fine while the README was the only place I described myself.

Then I wanted a real website with writing on it, and every fact suddenly had two homes. The bio, the mottos, the featured projects and the contact links would live in the README's config and again somewhere in the site. Every new post would need a title, date and link added to the README by hand. Two copies of the same words drift; it's only a question of how fast.

I also wanted more than a plain blog: diagrams I could still edit after publishing, a home page with some personality, and pages that stay light on a phone. Most ways of getting those extras quietly put a framework on every page.

## What I tried

1. **Keeping the README's config as the source.** The site could import `config.ts` directly. But then the site depends on the README build's code, and the data stays locked in a TypeScript file only one build understands.
2. **Making the site the source.** Generate the README from the built site. That turns a thirty-line template into a scraper, and the README build would need the whole site build to run first.
3. **Moving the data into plain files both builds read.** Bio, mottos, links and featured repos went into `content/site.json`, and posts into `content/posts/*.mdx`. `config.ts` became a few re-exports. Each build loads those files and ignores what it doesn't need.

For diagrams I weighed exported images first, then embedded a live Excalidraw canvas, and finally settled on an SVG rendered from the scene file.

## What worked

The shared folder. Each surface owns its layout, and neither owns the words.

### The README build

`readme.template.md` is about thirty lines: a fenced `whoami` block and a handful of HTML comment markers like `<!-- recent_posts_inject -->`. `index.ts` loads `content/site.json` (through a thin `config.ts`), fetches stats, featured repos and recent stars from the GitHub API, renders each block, and swaps it in for its marker.

The posts list doesn't need Astro. `posts.ts` reads the MDX files directly, pulls `title`, `date`, `slug`, `summary` and `draft` out of the frontmatter, skips drafts, and writes links to `/writing/<slug>` on this site. A GitHub Action runs the build when a push to `master` touches the content or the build scripts, and commits `README.md` only if it changed.

### The writing pipeline

On the site, posts are an Astro content collection loaded straight from `../content/posts`. The schema is where I put the rules I kept breaking by hand:

- `title` is at most 90 characters and `summary` at most 220, because the summary is reused as the meta description, the social card text, the RSS line and the `llms.txt` entry.
- `slug` must be kebab-case and must equal the file name. A small check fails the build otherwise, so a renamed file can't quietly change a URL.
- `draft: true` shows the post on the home page, `/writing/`, and its URL in `npm run dev:web`; lists mark it `Draft`, while production builds and feeds leave it out.

Every post follows the same section order: TL;DR, the problem, what I tried, what worked, what failed, architecture, code, results, and what I'd recommend. You're reading one. The order forces me to write down the failures, which is usually the part worth reading. A draft template in the repo, one that never ships, has the skeleton, and the post page builds its "On this page" rail, reading time and FAQ from the headings and frontmatter.

### Diagrams as SVG

A diagram is an Excalidraw scene saved as JSON under `web/diagrams/`, and in a post it's one line with no import:

```mdx
<ExcalidrawBoard src="/diagrams/board-pipeline.json" />
```

That line renders this:

<ExcalidrawBoard
  src="/diagrams/board-pipeline.json"
  height={420}
  caption="Build-time diagram pipeline: scene JSON bakes to SVG in Node, then inlines into static post HTML with zero React or Excalidraw shipped to the browser."
/>

In words: when `astro dev` or `astro build` starts, `web/scripts/bake-diagrams.mjs` runs in Node with `jsdom`, calls Excalidraw's `exportToSvg` on each scene under `web/diagrams/`, and writes the SVG to `web/.generated/diagrams/`. When a post renders `<ExcalidrawBoard />`, the Astro component reads that baked SVG and inlines it into the post HTML alongside a small pan-and-zoom script, so the browser never downloads Excalidraw or React. Hover the board and a small control bar shows up for zoom, reset and expand. Drag pans; the scroll wheel stays with the page.

Dark mode is one CSS filter on the SVG, the same invert-and-rotate Excalidraw uses for its own dark theme, so I draw every scene in light mode with dark strokes. The hand-drawn fonts are hosted here, so a board never reaches out to a CDN.

### A mood image on the home page

On desktop, the home page shows one still image next to the text, and it changes every visit. It's the most personal part of the site and the one with the most moving parts, so it gets its own section under Architecture.

### Command palette

Press <kbd>⌘K</kbd>, <kbd>Ctrl</kbd>+<kbd>K</kbd> or <kbd>?</kbd> anywhere for a palette of pages, posts and social links, plus "Toggle theme". There's no button for it. A 3.6 KB listener ships on every page; the palette itself is 5.4 KB of plain TypeScript, fetched on first open. Two-key chords (<kbd>G</kbd> then <kbd>W</kbd> for Writing) work without loading it at all.

### Themes without a flash

Pages ship dark. A tiny inline script in `<head>` applies a saved light choice before the first paint, so there's no flash of the wrong theme. The toggle writes to `localStorage`, and everything that has colour, including the diagrams, follows the `data-theme` attribute on `<html>`.

### GitHub cards and link previews

When a post talks about a repository or a pull request, I can drop in a card instead of a bare link:

```mdx
<RepoCard owner="rishi23root" repo="rishi23root" />
<PrCard owner="rishi23root" repo="rishi23root" number={21} />
```

<RepoCard owner="rishi23root" repo="rishi23root" />

<PrCard owner="rishi23root" repo="rishi23root" number={21} />

Both are filled in from the GitHub API when the site builds, so your browser never talks to GitHub, and the stars or the PR's state are as fresh as the last deploy. If the API is down or rate-limited, the card falls back to a plain labelled link and the build carries on.

Plain links get a lighter version. Hover a link to [this site's repository](https://github.com/rishi23root/rishi23root) or to [the pull request that added the diagrams and these cards](https://github.com/rishi23root/rishi23root/pull/21), and a small preview opens under it. The post page scans its own source for GitHub links at build time and renders a preview for each into the HTML. A short script shows the right one on hover or keyboard focus. On a phone, a tap just follows the link.

### Feeds and structured data

RSS, the sitemap, structured data and `llms.txt` are all generated from the same posts and `site.json`, so there's nothing hand-kept to go stale. The details are under Architecture.

## What failed

### The live Excalidraw canvas

My first version embedded the real Excalidraw app in view mode. Every board flashed an empty white canvas before the drawing appeared. The editor's stylesheet, about 145 KB, landed in the CSS shared by every post, with or without a board. I spent more CSS hiding Excalidraw's menus than styling the board. Swapping to SVG fixed all three.

### A CSS import that only worked sometimes

Excalidraw exports its stylesheet under `development` and `production` conditions, with no default. A plain `import '@excalidraw/excalidraw/index.css'` built fine and then failed in local dev with "Cannot find module". A Vite alias fixed it for me and not for everyone else. At the time, the real fix was not importing the package statically at all: loading it with a dynamic `import()` in the browser meant the server never tried to resolve it, before I moved the export to Node altogether.

### Letting the export inline its fonts

By default `exportToSvg` embeds the hand-drawn font inside the SVG. That means a 1.8 MB font-subsetting script, a worker that failed and fell back to the main thread, and a font fetched from a CDN. Turning that off and hosting the two fonts myself (118 KB total on disk, split by character range so a page fetches only the 24 KB Latin subset it uses) removed all of it.

### Trusting the first error message

After a dependency change, the dev server threw `jsxDEV is not a function` and the boards stayed blank. It looked like a broken component. It was a stale Vite pre-bundle cache. `rm -rf web/node_modules/.vite` and a restart fixed it. When a dev-only error makes no sense, clear the cache before reading the stack trace.

<Callout>A headless test browser can also lie to you: Chrome in headless mode reports `hover: none`, so styles meant for touch screens apply and hover-only UI looks permanently visible. Force a mouse pointer before trusting a hover test.</Callout>

### Two lists for the same six repos (fixed)

In the first version, the Projects page read `projects` from `site.json` while the README's Featured Work and `llms.txt` read a separate `opensource.active` and `opensource.blurbs` block. Those were the same six repositories typed twice, and one blurb drifted before I noticed. Commit `a7ae886e` removed `opensource` from `site.json` and moved `repo` and `featured` onto `projects[]`, so `config.ts` and `llms.txt.ts` now derive Featured Work from that single list.

## Architecture

In words: `content/` holds the data. The README build reads the bio and post titles and writes `README.md`, which GitHub shows on my profile. The Astro site reads everything and deploys to GitHub Pages. Two workflows run on pushes to `master`, each only when the files it depends on changed: one rewrites the README, the other deploys the site. Either can also be started by hand.

| Piece | Reads | Writes |
| --- | --- | --- |
| README build<br />`index.ts`, `posts.ts` | `site.json`, post frontmatter, GitHub API | `README.md` |
| Astro site<br />`web/` | `site.json`, full posts, board scenes | pages, RSS, sitemap, `llms.txt` |

The site imports the file directly through `site.ts`.

### Mood images

The catalogue is a list in `site.json`. Each entry has an `id`, a short activity `label`, the image path and alt text:

```json
{ "id": "shore", "label": "sitting", "src": "/mood/shore.webp", "alt": "Figure sitting on a beach shore under open sky" }
```

As of November 2026, the catalogue holds seven moods: cycling, wandering, roaming, exploring, tennis, sitting and sketching. Each is a portrait WebP between 15 and 80 KB in `web/public/mood/`. Adding one is an image and four lines of JSON.

On the home page they sit in a plate beside the text, and the caption has two controls: "next" and a link to every mood. Three decisions keep that cheap:

1. **Desktop only.** The plate is hidden below 1024px, and the React island that runs it hydrates with `client:media="(min-width: 1024px)"`. A phone gets the text and never downloads React or a single mood image.
2. **A shuffle bag, not random.** The order lives in `localStorage`. Every mood shows once before any repeats, a new round never opens with the image you just saw, and if I add or remove a mood the bag notices and starts over. Each full page load advances it by one, and "next" advances the same bag with a 420 ms crossfade.
3. **Pick before React.** The island would normally choose the mood after it hydrates, which means the image request starts late. Instead, an inline script in `<head>` runs the same shuffle-bag code, picks the mood, and adds a high-priority `<link rel="preload">` for that one image. React then adopts that pick instead of advancing again. Once the page has loaded and gone idle, the island quietly prefetches the next mood at low priority, so "next" is instant.

`/mood` shows the whole catalogue as a grid with each activity label, and every still links to `/?mood=<id>`, which forces that mood on the home page. The page is `noindex` and left out of the sitemap; it's a gallery, not something to rank.

### Projects and Featured Work

The Projects page reads `projects` from `site.json`: a title, a one-line blurb, a link, optional tags, and an `order` field to sort by, rendered as static HTML with a small search and tag-filter script. Two of the entries are upstream projects I contribute to; the rest are mine.

The README's Featured Work derives from the same list. `config.ts` keeps entries that define a `repo` (`owner/repo`) and don't set `featured: false`, ordered by `order`. On rebuild, `index.ts` asks the GitHub API for each repo's live star count and uses my `blurb` or falls back to the repo's own description. `llms.txt` and the home page's Work section read from the same list via `getFeaturedProjects()`.

### RSS

`/rss.xml` is a short endpoint. It takes the published posts, newest first, and maps each to a title, the post's `summary` as the description, the publish date and its link. Because it calls the same `getPublishedPosts()` as `llms.txt` and the redirects, a draft can't appear in the feed by accident. Every page advertises it with `<link rel="alternate" type="application/rss+xml">`, so feed readers find it from any URL.

### SEO and answer engines

Classic SEO and answer-engine optimisation (AEO: being quotable by assistants and AI search) turn out to want the same thing here: one clear answer, stated once, in a place a machine can find.

- **Canonical URLs.** Every page sets an absolute canonical with a trailing slash, matching how the site is built, so there's one address per page.
- **Social cards.** Open Graph and Twitter tags on every page, with the large-image card. A post uses its `image`, then its `cover`, then the site default, always as an absolute URL. Posts set `og:type` to `article` and add the publish time.
- **Structured data.** The home page describes me as a `Person`, with my social profiles as `sameAs`. Each post adds `BlogPosting` (headline, dates, keywords, image, author), a `BreadcrumbList` (Home, Writing, post), and `FAQPage` when the frontmatter has an FAQ. The FAQ is also rendered on the page, so the markup never claims something a reader can't see.
- **Sitemap and robots.** `@astrojs/sitemap` generates the sitemap at build time and skips `/mood` and the `/blog` redirects. `robots.txt` allows everything, names the main AI crawlers explicitly, and points to the sitemap.
- **`llms.txt`.** A plain-text summary for assistants, generated by an endpoint rather than kept in `public/`: who I am, my stack and links, featured work, key pages, and every published post with its date and one-sentence summary. It ends with a short note asking assistants to cite this site and not to invent bio claims.
- **Old links.** The writing section used to live at `/blog`. `/blog` redirects to `/writing/`, and a small page generates a redirect for every `/blog/<slug>`. Retired posts get the same treatment; this article replaced an older one, and its URL now points here. GitHub Pages can't send real 301s, so each old URL is a tiny page with a meta refresh and a canonical pointing at the new one.

The AEO part is mostly the writing, not the markup. Every post opens with an answer, the `summary` field is one sentence that still makes sense quoted alone, and FAQ answers are written to stand alone. The markup just makes that easy to find.

## Code

The README side is plain string work. This is the whole posts block:

```ts
export async function renderRecentPosts(
  siteUrl: string,
  limit = 5,
): Promise<string> {
  const posts = (await listPosts()).slice(0, limit)
  if (!posts.length) return '_No posts yet._'
  const base = siteUrl.replace(/\/$/, '')
  return posts
    .map((p) => {
      const url = `${base}/writing/${p.slug}/`
      return `- **[${escapeMd(p.title)}](${url})** — ${p.date}`
    })
    .join('\n')
}
```

The site side leans on the schema. Trimmed to the parts that matter:

```ts
const posts = defineCollection({

```

And the diagram export, which runs in Node while the site builds, trimmed to its two ends. `registerHooks()` has to run before the package import, or Node rejects a JSON file inside the package:

The mood preload is the one slightly unusual trick. The shuffle-bag function is self-contained on purpose, so the home page can turn it into a string and inline it into `<head>` with the catalogue:

```ts
export function firstMoodPreloadScript(moods: MoodSlot[]): string {
  const args = [moods.map(({ id, src }) => ({ id, src })), MOOD_CYCLE_KEY, DESKTOP_MQ]
    .map((v) => safeJson(v))
    .join(',')
  return `(${preloadFirstMood})(${args},${createMoodBag})`
}
```

The head script and the React island run literally the same shuffle code, so they can't disagree about which mood comes next. `safeJson` is `JSON.stringify` with `<` escaped, which keeps a stray character in the data from closing the script tag.

## Results

I measured these from the production build (`npm run build:web`) and the browser's network panel. Sizes are uncompressed unless marked gzipped. The first column is the earlier live-canvas version of the boards; the second is what ships now:

| Metric | Live Excalidraw canvas (before) | Build-time baked SVG (now) |
| --- | --- | --- |
| Editor CSS on posts | ~145 KB | 0 KB |
| Client JS for boards | React + Excalidraw bundle | 7.6 KB inline pan/zoom (2.3 KB gzipped) |
| Font-subsetting worker | ~1.8 MB + CDN font fetch | 0 KB (24.4 KB Latin WOFF2 self-hosted) |
| Initial paint | Empty whiteboard flash | Immediate SVG in HTML, works without JS |

- **One edit, both surfaces.** Changing my bio or publishing a post is one commit. The README and the site both pick it up on the next push to `master`, with no copy step.
- **A plain post ships no React.** Measured from `web/dist/` after `npm run build:web`: `hello-world` references two small external scripts — the post rail script at 9.1 KB (3.8 KB gzipped) and the command palette listener at 3.6 KB (1.6 KB gzipped) — and no React. The shared stylesheet is 43.9 KB (9.4 KB gzipped), and the home page HTML is 27.3 KB (8.6 KB gzipped).
- **Diagrams do not ship the editor.** None of the client JS files in `web/dist/_astro/` contain `@excalidraw/excalidraw`. The writing post's HTML does not reference the React chunk (207.8 KB, 64.3 KB gzipped). Pan and zoom are one 7.6 KB inline script (2.3 KB gzipped). The SVG is already in the HTML.
- **GitHub cards are plain HTML.** They ship no script at all. Link previews add a 2.7 KB inline script (1.2 KB gzipped), and only to posts that link to a repo or PR.
- **Diagrams got lighter.** Moving from the live canvas to SVG took ~145 KB of CSS off every post. Self-hosting fonts took a ~1.8 MB script and a CDN request off every board.
- **Mood images cost phones nothing.** The seven stills total about 400 KB, but a desktop visit downloads one up front plus one low-priority prefetch after load, and a phone downloads none.
- **Feeds stay in sync for free.** RSS, `llms.txt` and [the sitemap](/sitemap-index.xml) rebuild on every deploy. The sitemap lists the home page, Projects, Writing and every published post. `web/astro.config.mjs` filters out `/mood/`, `/blog/` and `/404`, and a draft never shows up because production doesn't build its page.
- **Every post ships three kinds of structured data** when it has an FAQ (`BlogPosting`, `BreadcrumbList`, `FAQPage`), all from frontmatter I was writing anyway.
- **Drafts can't leak.** One flag hides a post from pages, RSS, the sitemap, `llms.txt` and the README list, because all five are built from the same field.

## What I recommend

Share data, not layout. A JSON file and a folder of MDX are boring on purpose: any build can read them, and none of them owns the others. The README generator here is a template, a few markers and string replacement. Keep yours that dumb.

Make JavaScript earn its place per page. Here, Astro's `client:media` directive keeps the desktop-only mood plate off phones, and everything else either bakes at build time or ships as a tiny targeted script.

If you embed diagrams, bake them to SVG when the site builds. The page has the drawing with no editor library, and a browser with JavaScript off still shows it. Keep Excalidraw installed for that bake and nowhere else. Import it from Node only after registering module hooks that can handle its JSON and CSS, and don't inline the fonts.

Don't do this if you only want a blog. A hosted platform will get you writing sooner. This setup pays off when you have more than one surface to keep in sync and you'd rather edit a file than a dashboard.
